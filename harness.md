# Ghost Protocol — Governance Harness (v6.0)

**Updated:** 2026-03-27
**Supersedes:** v5.0 (2026-03-24)
**Purpose:** Complete manifest of the governance harness. Any agent should be able to rebuild the entire harness from this file.

---

## Core Principle

Every code change goes through a gated commit process. Hooks are the enforcement points. If a gate fails, work is BLOCKED. No exceptions. No carve-outs. If governance doesn't account for a situation, STOP → discuss with operator → revise governance → re-run.

## 2. Hook Specifications

### Hook 0: Captain Pre-Tool (captain-check.sh)

**Trigger:** Before every Bash, Edit, Write, Agent tool call FROM THE GOVERNOR ROOT
**Config:** `triad-governor-v2/.claude/settings.json` → `hooks.PreToolUse`
**Location:** `triad-governor-v2/.claude/hooks/captain-check.sh`

| Check | What it does | Blocks? |
|-------|-------------|---------|
| Active app | Reads session-state.md for Active App field | No — informational if missing |
| Sprint sequence | Reads app's sprints.json executionSteps | Yes — blocks if Ghost gate pending |
| Ghost gate enforcement | Checks phase-{N}-verification.md exists before next step | Yes — exit 2 |
| Ghost messages | Reads app's ghost_messages.json | Yes — exit 2 for write operations |
| Delegation enforcement | During in_progress sprint: Bash/Edit/Write on app files BLOCKED. Only Agent dispatch, reads, sprint management, evidence writes, governor infra allowed. | Yes — exit 2 |
| Audit logging | Writes to app's evidence/{sprint}/workflow-audit.log | No — informational |

**This hook governs Captain.** Captain can ONLY delegate via Agent dispatch during active sprints. Any direct Bash/Edit/Write on app files is blocked with explicit error. The app-level hook (context-check.sh) governs Dev and Ghost. Both are needed.

### Hook 1: Pre-Tool (context-check.sh)

**Trigger:** Before every Bash, Edit, Write, Agent tool call FROM THE APP DIRECTORY
**Config:** `.claude/settings.json` → `hooks.PreToolUse`
**Location:** `.claude/hooks/context-check.sh`

| Check | What it does | Blocks? |
|-------|-------------|---------|
| Session freshness | Reads session-state.md mtime, blocks if >4 hours stale | Yes — exit 2 |
| Sprint sequence | Reads sprints.json executionSteps, identifies current step | Warning if Ghost gate pending (blocks writes) |
| Ghost messages | Reads ghost_messages.json for unacknowledged BLOCK directives | Yes — exit 2 for write operations |
| Audit logging | Writes timestamp + tool name + step number to workflow-audit.log | No — informational |
| Git state | Reports branch and dirty state | No — informational |

**Escape hatches:**
- Writes to session-state.md are always allowed (prevents deadlock)
- Read-only operations (Read, Glob, Grep) are never blocked

### Hook 2: Pre-Commit (pre-commit.sh)

**Trigger:** On `git commit`
**Config:** `.git/hooks/pre-commit` (copy of `scripts/pre-commit.sh`)
**Install:** `cp scripts/pre-commit.sh .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit`

| Gate | Check | Blocks? |
|------|-------|---------|
| 1 | COMMIT_ROLE and COMMIT_SPRINT env vars set, sprint exists in sprints.json | Yes |
| 1.5 | Previous sprint in sprints.json is committed or parked (chain of custody) | Yes |
| 1.6 | Fresh watchdog scan + acknowledgment of any violations | Yes |
| 1.7 | Session state references current sprint | Yes |
| 1.8 | Ghost messages — no unacknowledged BLOCK directives | Yes |
| 1.9 | All executionSteps in sprints.json have status "completed" | Yes |
| 1.10 | Exit gate verdict "EXIT GATE: CLEARED" exists in post-sprint-report.md | Yes |
| 2 | Evidence directory exists and is non-empty | Yes |
| 2.5 | Pre-execution report has ## Declared Files, all staged app files listed | Yes (full governance) |
| 2.6 | Pre-exec predates post-sprint by 5+ minutes (anti-retroactive) | Yes (full governance) |
| 3 | Enforcer checklist contains RESULT: APPROVED | Yes (full governance) |
| 4 | Cross-sign: APPROVED verdict, different roles, fresh timestamp | Yes (full governance) |
| 5 | All staged files within COMMIT_ROLE scope | Yes |
| 6 | EF checks: TypeScript (EF-01), governance file protection (EF-05), UI rendering guard (EF-14), UI permission gate (EF-18), data array guard (EF-15), UI element guard (EF-16), locked value guard (EF-17) | Yes |
| 7 | Hook integrity — installed hook matches source | Warning |

**Required environment variables:**
```bash
COMMIT_ROLE=<role> COMMIT_SPRINT=<sprint-id> git commit -m "message"
```

**Valid roles:** frontend, backend, test, integration, scribe, enforcer, architect, orchestrator, governance

**Light governance:** V-*, E-*, T-*.EXIT sprints and governance role skip Gates 2.5, 2.6, 3, 4.

## 3. Sprint Construction Protocol

### Sources

**From plan.md (core workflow):**
Each plan.md section defines a body of work. Captain translates sections into sprints. Sprint `source` field references the section.

**From issues.md (remediation):**
Captain groups issues by domain dimension (FE/BE/DT/AU/IN) and creates remediation sprints. One sprint per domain. Sprint `source` field lists the issue IDs.

### Construction Steps

1. **Gather** — Collect items from plan.md section OR issues.md by domain
2. **Group** — One sprint per domain. If >10 issues in a domain, split into multiple sprints.
3. **Name** — `<prefix>-<NNN>` per category table (P, R, G, I, E, M, D, T, L, U, CL, CV, J)
4. **Write ACs** — Described, not bare IDs. Format: `"R-014.B1: Tour overlay dismissed and stays dismissed across navigation"`
5. **Write A-gates** — Entry criteria for this sprint (references standard ghost gate protocol)
6. **Write B-gates** — Exit criteria mapped to ACs
7. **Write executionSteps** — Dev phases interleaved with Ghost gates
8. **Set source** — `"plan.md §3"` or `["I-149", "I-150"]`
9. **Set status** — `proposed`. Requires operator authorization to proceed.

### Wave Formation

Sprints in different domains can parallelize. Same domain must serialize. `parallelizable: true` + no `declaredFiles` overlap = same wave.

### sprints.json Schema

- executionSteps is the timestamped audit trail. Captain updates status/timestamp as each completes.
- Every Dev phase is followed by a Ghost verification step. No exceptions.

## 4. Ghost Protocol

### Principle

Ghost and Dev never communicate directly. They communicate through files. Hooks enforce that neither side can ignore what the other wrote.

### Dead Drop: ghost_messages.json

```json
{
  "messages": [
    {
      "id": "GM-20260327-001",
      "type": "BLOCK",
      "timestamp": "2026-03-27T08:00:00Z",
      "message": "7 MAJOR defects open. FIX sprint required before next QA sprint.",
      "defects": ["I-149", "I-150"],
      "acknowledged": false,
      "acknowledgedBy": null,
      "acknowledgedAt": null
    }
  ]
}
```

**Types:** BLOCK (must acknowledge before commit), WARN (informational), INFO (logged only)
**Enforcement:** Pre-tool hook blocks write operations if unacknowledged BLOCK exists. Pre-commit Gate 1.8 blocks commit.

### Entry Gate (A-Gates)

Run BEFORE sprint work starts. Ghost reads entryGates from sprints.json for the sprint, runs each check, writes verdict into `evidence/{sprint}/pre-execution-report.md`.

Standard A-gates (adapt per sprint):
```
A1: Previous sprint exit gate cleared
A2: Worktree clean (no application files modified)
A3: Session state references this sprint
A4: Pre-execution report exists
A5: Pre-exec has ## Objective
A6: Pre-exec has ## Test Plan with specific commands
A7: Pre-exec has ## Declared Files
A8: Declared files match sprints.json
A9: Ghost messages clear
```

**Verdict format (appended to pre-execution-report.md):**
```
## Ghost Entry Gate
**Reviewed by:** ghost-agent
**Timestamp:** [date -u +%Y-%m-%dT%H:%M:%SZ]
**Sprint:** [sprint-id]
**A1 Previous cleared:** [PASS/FAIL/SKIP]
**A2 Worktree:** [PASS/FAIL]
...
**ENTRY GATE: APPROVED** or **ENTRY GATE: REJECTED — [list failures]**
```

Dev checks: `grep "ENTRY GATE: APPROVED" evidence/{sprint}/pre-execution-report.md`

### Exit Gate (B-Gates)

Run AFTER sprint work completes. Ghost reads exitGates from sprints.json, verifies each against the actual work product, writes verdict into `evidence/{sprint}/post-sprint-report.md`.

Standard B-gates (adapt per sprint):
```
B1-BN: Sprint-specific AC verifications (mapped to exitGates in sprints.json)
B(N+1): Commit exists with correct sprint ID
B(N+2): Entry gate was approved
B(N+3): Test file exists and was run with output
B(N+4): AC results table complete (count matches sprints.json)
B(N+5): Worktree clean
B(N+6): Ghost messages clear
```

**Verdict format (appended to post-sprint-report.md):**
```
## Ghost Exit Gate
**Reviewed by:** ghost-agent
**Timestamp:** [date -u +%Y-%m-%dT%H:%M:%SZ]
**Sprint:** [sprint-id]
**B1 [description]:** [PASS/FAIL]
**B2 [description]:** [PASS/FAIL]
...
**EXIT GATE: CLEARED** or **EXIT GATE: NOT CLEARED — [list failures]**
```

Dev checks: `grep "EXIT GATE: CLEARED" evidence/{sprint}/post-sprint-report.md`

### Inter-Phase Verification

Between Dev phases within a sprint, Ghost verifies the phase output before the next phase can start. This is NOT a full A/B gate — it's a focused check that the phase deliverables exist and are correct.

Ghost reads the executionSteps array, finds the current Ghost verification step, runs the check described in the step's `action` field, writes a verification report, and updates the step status/timestamp.

**Evidence file:** Ghost writes each inter-phase verdict to `evidence/{sprint}/phase-{N}-verification.md` where N is the step number from executionSteps.

**Format:**
```markdown
## Phase Verification — Step {N}
**Reviewed by:** ghost-agent
**Timestamp:** [date -u +%Y-%m-%dT%H:%M:%SZ]
**Sprint:** [sprint-id]
**Step:** {N} — [action description from executionSteps]
**Checks:**
- [check 1]: [PASS/FAIL — evidence]
- [check 2]: [PASS/FAIL — evidence]
**PHASE VERIFIED** or **PHASE FAILED — [list failures]**
```

**Hook enforcement:** The pre-tool hook checks: if the current executionStep is a Ghost gate, the corresponding `phase-{N}-verification.md` must exist and contain "PHASE VERIFIED" before the next Dev step can proceed. Write operations are BLOCKED if the verification file is missing.

## 5. Role Enforcement

| Role | Can Modify | Cannot Modify |
|------|-----------|---------------|
| Orchestrator | Governance files, evidence/, sprints.json, sprint-scoped app files | — |
| Builder (backend) | server/ files | client/, scripts/, governance |
| Builder (frontend) | client/ files (only when uiPermissions allows) | server/, scripts/, governance |
| QA Tester | Read code, run tests, capture screenshots | Modify any files except evidence/ |
| Enforcer | Evidence review only | Application code |
| Ghost | Scan, report, write directives, write gate verdicts | Modify application code |
| Explorer | Read code, search, analyze | Modify any files |

**Mechanical enforcement:** Pre-commit Gate 5 checks staged files against COMMIT_ROLE scope.
**Behavioral enforcement:** CLAUDE.md rules, agent-specific `.governor/prompts/*/CLAUDE.md` files.

### Agent Isolation Model

Ghost and Dev are **isolated agents** — dispatched independently with NO team membership. They cannot message each other. They communicate through files only.

| Agent | Dispatch | Can message | Communicates via |
|-------|----------|-------------|-----------------|
| Ghost | Independent (no team) | Nobody | Files only (ghost_messages.json, phase-N-verification.md) |
| Dev | Independent (no team) | Nobody | Files only (evidence reports) |
| Researcher | Team member (optional) | Captain, other advisors | Messages + files |
| Skeptic | Team member (optional) | Captain, other advisors | Messages + files |

**Why isolation matters:** Ghost verifies Dev's work. If they can communicate directly, Ghost can be influenced by Dev and the verification is worthless. The file is the only interface between execution and verification.

**Mechanical enforcement:** captain-check.sh blocks Agent dispatch with `team_name` when the agent name is ghost, dev, implementer, or verifier (exit 2).

**The file chain:** Ghost writes verdict → Captain reads verdict → Captain dispatches Dev → Dev reads verdict → Dev works → Dev writes report → Captain reads report → Captain dispatches Ghost → Ghost verifies.

## 6. UI Protection

Frontend UI files (`client/src/pages/`, `client/src/components/`) are PROTECTED by default.

1. Every sprint has a `uiPermissions` field in sprints.json
2. `NONE` → pre-commit EF-18 BLOCKS any staged UI files
3. `DECLARED:` → must list UI changes in pre-exec, Gate 2.5 validates
4. EF-14 limits UI page changes to 40 lines per file (override with `UI_EXCEPTION=true`)

## 8. Sprint Lifecycle

### Status Transitions

```
proposed → approved → in_progress → committed
                 ↘ parked (add parkedReason)
```

- `proposed`: Captain defined it. Not executable.
- `approved`: Operator reviewed pre-execution criteria and explicitly authorized.
- `pre-authorized`: Operator authorized autonomous execution of multiple sprints.
- `in_progress`: Work underway. Ghost entry gate passed. Max 1 at a time.
- `committed`: Done. Ghost exit gate cleared. Commit hash recorded.
- `parked`: Paused. Remaining work tracked.

### Execution Sequence (per sprint)

1. Captain builds sprint in sprints.json (ACs, gates, executionSteps)
2. Captain presents pre-execution criteria to operator
3. Operator says "go" → status changes to `approved`
4. Ghost runs entry gate (A-gates from sprints.json) → verdict in pre-exec
5. Status changes to `in_progress`
6. Dev executes phase 1
7. Ghost verifies phase 1 (inter-phase gate)
8. Dev executes phase 2 (repeat Dev→Ghost for each phase)
9. Dev writes post-sprint-report.md
10. Ghost runs exit gate (B-gates from sprints.json) → verdict in post-sprint
11. Run enforcer-checklist.sh
12. Write cross-sign.md (different role reviews)
13. Commit: `COMMIT_ROLE=<role> COMMIT_SPRINT=<sprint-id> git commit -m "message"`
14. Update sprints.json with commitHash, move to sprints.backlog.json

### Required Artifacts Per Sprint

| File | Content | Timing |
|------|---------|--------|
| `pre-execution-report.md` | Objective, Declared Files, Test Plan, UI Changes (if applicable), Ghost Entry Gate verdict | Before work |
| `post-sprint-report.md` | AC Results table, Test Execution output, UI Delta, Regression Delta, Ghost Exit Gate verdict | After work |
| `cross-sign.md` | Implementing Role, Reviewing Role, Verdict: APPROVED | Before commit |
| `enforcer-checklist.txt` | RESULT: APPROVED | Before commit |
| `workflow-audit.log` | Timestamped tool calls with step context | During work (auto) |

### Watchdog Acknowledgment

When violations are found, write `evidence/watchdog-ack.txt`:
- Required fields: Acknowledged-By, Sprint, Timestamp
- Must address every violation check ID
- Must be less than 60 minutes old
