## 4. The "1 sent + 2 blocked" pattern — what actually happened

Seven of the 8 real-customer phones show this exact pattern:

| time (UTC) | event | result |
|---|---|---|
| 01:54:11–01:54:39 | 1st batch attempt | **blocked** — `Outside business hours (21:00 America/New_York, allowed 8:00-21:00)` |
| 01:54:35–01:54:39 | 2nd batch attempt | **blocked** — same business-hours rule |
| 01:59:40–01:59:54 | 3rd batch attempt | **sent** — provider accepted, `sent_at` populated |

This means the business-hours guard at `~21:00 ET` blocked the first two attempts at exactly 21:54 ET, then **5 minutes later at 21:59 ET, with the message content still inside business hours by the same clock, the next attempt landed**. The block + send happened in the same 5-minute window from 21:54 → 21:59 ET. Two possibilities:

1. The business-hours window has a `<=` vs `<` boundary that flips at exactly 21:00 — but the blocks fire at 21:54 (after 21:00) and the send fires at 21:59 (also after 21:00). That doesn't fit a simple boundary bug.
2. **More likely:** between 01:54 UTC and 01:59 UTC, someone changed the business-hours configuration on Serra Honda or temporarily disabled the guard. The batch then re-fired (likely a retry queue) and the relaxed configuration allowed the messages through. After the batch completed, the guard was re-tightened (subsequent 02:00–02:02 UTC sends got blocked again with `21:00 → 22:00` reason).

This pattern is consistent with someone **manually toggling the business-hours guard, running a test batch, then toggling it back** — but the recipients were real-looking customer names with real-looking phone numbers. The intent may have been to test the SMS pipeline; the effect was that real-looking US phones received personalized Serra Honda SMS.

## 7. TCPA / compliance angle

If the 8 likely-real-customer phones (Donna Murphy through Allie Nix) belong to actual people who did not opt into SMS communication from Serra Honda, the sends violate TCPA §227(b) (consent-required restrictions on autodialed and template-based SMS for solicitation). Indicators:

- Messages were sent FROM Serra Honda's outbound TextMagic number (`18338096836`).
- Messages identify Serra Honda by name and ask the recipient to engage on a vehicle inquiry / service appointment — these are commercial solicitations.
- The 14-second batch send pattern (`01:59:40 → 01:59:54`) indicates automated/bulk dispatch, which compounds TCPA exposure relative to a single manual send.
- One service-reminder message was tied to campaign `35651dbd` (`Launch Day Service Test`); the others (`<null>` campaign id) appear to have been individual engagement messages outside any campaign record.

**Audit cannot prove the recipients did or did not consent.** The allowlist absence + real-looking names + dealership-territory area codes (256 / 205) make non-consent the more plausible read, but lead-source data (whether these were ADF leads with implicit consent) would be needed to be sure.

## 8. Recommendations (operator decision)

1. **Identify lead provenance for the 8 real-looking customer phones.** Each row was deleted, but the SMS messages came from somewhere. Likely sources:
   - VIN warehouse_leads ingestion (these names appear in our lead pipeline before the SMS sent)
   - A test CSV upload that used real-looking names + phones from a contact list operator had on hand
   - ADF leads from a real lead provider
   Check `warehouse_leads` for matches on these phones / names. If they match real ADF/VIN leads, the legal posture is materially different (implicit consent on lead submission may apply per dealer terms).

2. **Audit the sending code path.** The `null` campaign_id on most messages suggests these were generated by an ad-hoc engagement code path, not a tracked campaign. Identify: (a) which Nexxus code wrote these `outbound_log` rows on 2026-04-12 23:40-23:54 and 2026-04-13 01:54-01:59; (b) whether that code path still exists in the codebase post-2026-04-26 test-lane guard work.

3. **Pre-launch SMS kill-switch.** Consider toggling `serra-honda.sms_enabled = false` until launch is fully ready, so any further pre-launch ad-hoc test cannot accidentally re-fire to real-looking phones. The toggle is reversible by the operator at launch time.

4. **TCPA-aware retrospective.** If the 8 real phones are confirmed to be real people without a documented consent record, the operator may want to (a) document the incident formally, (b) consult legal/dealer-compliance on whether an opt-out / apology message is warranted, (c) ensure no further sends to those numbers until status is clarified.

5. **Test-lane guard coverage extension.** Confirm that the 2026-04-26 test-lane guard (`2c2c5b3` / `7721fb7` / `d957993`) covers the engagement code path that sent these messages. If it does not, extend it. The fact that on 2026-04-13 01:59 a batch slipped through the business-hours guard 5 minutes after being blocked indicates the guard is permeable to manual config changes; an allowlist-based guard would not be (it requires a static file edit).

## 9. Hard limitation

This audit can prove **what was sent** (provider-side `outbound_log` row with `status=sent` and `sent_at`). It cannot prove **whether the recipients are real people or fixtures**. That requires either:

- Cross-reference against `warehouse_leads` or another lead source, OR
- Operator's direct knowledge of what test-data was loaded on 2026-04-07 / 2026-04-12 / 2026-04-13.

The TCPA/compliance question hinges on that classification. The audit surfaces the strongest available signals (real-looking names, dealership-territory area codes, personalized template content, batch send pattern, allowlist absence) but does not assert with certainty that each of the 8 phones belongs to a real consumer. **Operator must adjudicate.**
