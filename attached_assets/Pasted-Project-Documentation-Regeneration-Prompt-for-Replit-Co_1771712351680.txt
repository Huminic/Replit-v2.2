Context and Objective

A comprehensive UI redesign has been completed that represents the true north for the platform, and you must now create governing documents that will guide Claude Code to bring this new UI to life.

Critical Guidance for Document Creation
1. UI as Source of Truth
The current working UI in Replit represents the validated design. When conflicts arise between legacy documentation and the current UI:
* UI wins
* Document what the UI shows, not what old docs say
* Describe the actual component hierarchy, data flow, and user interactions visible in the code
2. Acceptance Criteria as Validation Framework
Every requirement in NEW_SRS.md must trace to one or more items in the Functional Acceptance Criteria document:
* Add "Validates: [AC Section/Item]" references
* If an old requirement doesn't support new acceptance criteria, discard it
* If new acceptance criteria introduce requirements not in old docs, add them
3. Metric Specifications are Mandatory
The new 4-tile dashboard is THE centerpiece of the redesign:
* Include exact formulas from —Org admin Metrics - Main - org admin.md
* Specify data sources for each component of the formula
* Define drill-down modal contents
* Specify role-based visibility
* Do not dilute or modify these specifications
4. Extract, Don't Copy
From legacy documents:
* Extract: Architectural decisions, security principles, data source details, valid business rules
* Don't copy: Old UI specs, deprecated features, implementation details now obsolete
5. Be Specific and Actionable
Claude Code needs concrete guidance:
* ✅ "Create Pipeline Health Score tile at position (0,0) displaying formula: Win Rate × 50pts + Active Quality × 30pts + Freshness × 20pts"
* ❌ "Implement dashboard metrics"
* ✅ "File: client/src/pages/dashboard.tsx, Line 150: Add click handler to open drill-down modal"
* ❌ "Add interactivity to tiles"
6. Maintain Consistency
* Use consistent terminology across all documents
* Reference the same section numbers when cross-linking
* Use the naming conventions established in NEW_CONSTITUTION.md
* Keep RBAC tier names consistent (Super Admin, Partner Admin, Org Admin, Staff)
7. Prioritize Clarity Over Completeness
* If an old requirement is ambiguous and not visible in the current UI, discard it
* If you can't verify a requirement against the current codebase or acceptance criteria, flag it as "TBD - requires clarification"
* It's better to have 200 clear, actionable requirements than 500 vague ones
