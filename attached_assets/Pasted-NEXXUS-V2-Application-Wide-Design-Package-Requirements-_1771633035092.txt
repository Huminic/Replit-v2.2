NEXXUS V2 — Application-Wide Design Package Requirements for Developer Handoff
                                                                                                                                                                                                                          
  Purpose                                                                                                                                                                                                                 
                                                                                                                                                                                                                          
  A developer (Claude Code) will receive this design package and implement every page, component, and interaction across the entire application. The developer has a separate SRS defining what features do. The developer
   does NOT need functionality specs from the designer. The developer DOES need:                                                                                                                                          

  - Structural annotations embedded in every mockup
  - A complete design token system
  - Component-level documentation with implementation cues
  - State and error treatment specifications
  - Testing support baked into the designs
  - Accessibility contract

  This document defines what must be in the design package for the developer to implement and test without guessing, asking questions, or making visual decisions.

  ---
  1. INLINE CUE SYSTEM (Embedded in Every Mockup)

  Every mockup delivered must contain developer cues as small, non-intrusive annotations (gray tags, margin notes, or an annotation layer that can be toggled on/off).

  1A. Data Test IDs

  Every element a user can interact with gets a data-testid annotation. The developer uses these for E2E tests (Playwright). Without them, the developer has to invent IDs and may not match the design intent.

  Convention: {element-type}-{context}-{descriptor}

  Buttons:     data-testid="button-save-settings"
  Inputs:      data-testid="input-search-leads"
  Toggles:     data-testid="toggle-dark-mode"
  Tabs:        data-testid="tab-integrations"
  Cards:       data-testid="card-agent-automa"
  Rows:        data-testid="row-lead-{id}"
  Modals:      data-testid="modal-confirm-delete"
  Dropdowns:   data-testid="select-role-filter"
  Links:       data-testid="link-view-details"
  Badges:      data-testid="badge-status-active"
  Menus:       data-testid="menu-user-profile"
  Menu Items:  data-testid="menu-item-logout"

  Rule: If a user can click it, type in it, toggle it, select it, or tab to it — it gets a test ID.

  1B. Data Slot Markers

  Anywhere dynamic data renders, use double-brace placeholders with a descriptive binding path. This tells the developer exactly what data feeds each text region.

  {{user.name}}
  {{org.name}}
  {{metric.value | number}}
  {{metric.label}}
  {{lead.status | badge}}
  {{item.createdAt | relative}}     ← "3 hours ago"
  {{item.createdAt | date}}         ← "Feb 21, 2026"
  {{list.length}} items
  {{percentage | percent}}          ← "42%"
  {{currency | usd}}                ← "$1,250.00"

  For lists/repeaters, annotate the container:

  [repeats: leads]
    {{lead.name}} · {{lead.phone}} · {{lead.status | badge}}
  [/repeats]

  For conditional text:

  [if: items.length === 0] "No results found" [/if]
  [if: items.length > 0] "{{items.length}} results" [/if]

  1C. State Annotations

  Every component that has multiple visual states must be annotated with which state the mockup shows and a list of all other states:

  [State: LOADED — showing 12 items]
  Other states:
    LOADING → skeleton rows (see skeleton spec)
    EMPTY → empty illustration + CTA
    ERROR → error banner + retry
    FILTERED_EMPTY → "No results match your filters" + clear filters link

  The developer needs at least one visual example of each state, or a reference to the state catalog (Section 6).

  1D. Interaction Annotations

  For any behavior that isn't obvious from the static mockup, add a directional note:

  → On click: expand accordion section
  → On hover: show tooltip "{{tooltip.text}}"
  → On change: debounce 300ms, then filter list
  → On blur: validate format, show error if invalid
  → On drag: reorder list items (save on drop)
  → On long-press (mobile): show context menu
  → On double-click: enter inline edit mode
  → On scroll to bottom: load next page (infinite scroll)
  → On submit: disable form, show spinner in button
  → On success: toast notification, auto-dismiss 3s
  → On error: inline error message below field, field border turns red

  1E. Conditional Visibility Markers

  Mark elements that appear/disappear based on conditions:

  [visible-when: user.role <= 3]          ← Org Admin and above
  [hidden-when: list.length === 0]
  [disabled-when: form.isSubmitting]
  [collapsed-by-default]
  [expanded-when: item.isSelected]
  [role-gated: super_admin]               ← Super Admin only
  [role-gated: partner_admin+]            ← Partner Admin and above
  [feature-flag: sms_enabled]             ← Only if SMS is configured

  1F. Layout Annotations

  For every container, annotate the layout mechanism:

  [flex: row, gap-4, items-center]
  [grid: 3-col, gap-6, responsive → 2-col @ tablet → 1-col @ mobile]
  [sticky: top-0, z-10]
  [overflow: scroll-y, max-h-[calc(100vh-64px)]]
  [aspect-ratio: 16/9]

  --shadow-xs:    ← subtle lift (hover states)

  --shadow-lg:    ← modals, dialogs

  2F. Motion & Transitions

  --duration-instant:  0ms        ← toggles, checkboxes
  --duration-fast:     100ms      ← hover states
  --duration-normal:   200ms      ← most transitions
  --duration-slow:     300ms      ← panel open/close
  --duration-slower:   500ms      ← page transitions

  --ease-default:      cubic-bezier(0.4, 0, 0.2, 1)
  --ease-in:           cubic-bezier(0.4, 0, 1, 1)
  --ease-out:          cubic-bezier(0, 0, 0.2, 1)
  --ease-bounce:       cubic-bezier(0.34, 1.56, 0.64, 1)

  Document which transitions apply to which interactions:
  - Hover color changes: duration-fast ease-default
  - Panel slide: duration-slow ease-out
  - Modal fade: duration-normal ease-default
  - Toast enter: duration-normal ease-bounce
  - Skeleton pulse: duration-slower ease-in-out, infinite

  2G. Breakpoints

  lg:    1024px    ← small laptops

  4. PATTERN LIBRARY

  Document recurring UI patterns used across multiple pages. The developer builds these once and reuses them.

  4A. List + Detail Pattern

  Many pages follow: list on left → detail on right (or full-width list → click to open detail).

  Document:
  - Split ratio (e.g., 40/60, 35/65)
  - Whether detail is inline panel, sheet, or separate route
  - What the list row contains (avatar + title + subtitle + status + timestamp)
  - How selection is indicated (background highlight, left border accent)
  - Mobile behavior (full-width list → tap to navigate to detail page)

  4B. Form Pattern

  Standard form layout used across settings, create/edit flows:

  Document:
  - Label position (above input vs inline)
  - Required field indicator (asterisk, "(required)" text, or color)
  - Error message position (below field, inline, or toast)
  - Form section grouping (card per section, or dividers)
  - Button placement (sticky bottom bar, inline right-aligned, or full-width on mobile)
  - Unsaved changes indicator (dot on tab, banner, or dialog on navigate away)

  4C. Table Pattern

  Standard data table used for leads, agents, users, etc:

  Document:
  - Header style (sticky, sortable indicators, column resize handles)
  - Row hover treatment
  - Selection checkboxes (if applicable)
  - Pagination vs infinite scroll
  - Column density (compact, default, relaxed)
  - Empty state within table
  - Loading state (skeleton rows)
  - Bulk action bar (appears when rows selected)

  4D. Card Grid Pattern

  Used for dashboards, agent lists, widget lists:

  Document:
  - Grid columns per breakpoint
  - Card minimum width
  - Card internal padding
  - Card hover treatment
  - Card selected state
  - Overflow behavior (scroll vs wrap)

  4E. Metric Display Pattern

  Used for dashboard numbers, health scores, KPIs:

  Document:
  - Large number + unit formatting
  - Trend indicator (arrow + percentage + color)
  - Sparkline/mini-chart placement
  - Click behavior (drill-down or modal)
  - Stale data indicator (how old data is shown differently)
  - Loading skeleton shape

  4F. Notification/Alert Pattern

  Used for toasts, banners, inline warnings:

  Document:
  - Toast position and stack direction
  - Banner types (info, warning, error, success) with icon + color
  - Dismissible vs persistent
  - Action buttons within alerts
  - Auto-dismiss timing per severity

  6. STATE CATALOG

  A STATE_CATALOG.md documenting every possible visual state for every major view type. The developer uses this to ensure no state is unhandled.

  Template Per View

  ## [View Name]

  ### Data States
  | State | Trigger | Visual Treatment |
  |-------|---------|-----------------|
  | Loading | Initial fetch | Skeleton matching content layout |
  | Loaded | Data received | Normal render |
  | Empty | Zero items | Empty illustration + heading + subtext + CTA button |
  | Filtered Empty | Filters active, zero matches | "No results match" + "Clear filters" link |
  | Error | API failure | Error card: icon + message + "Retry" button |
  | Stale | Data older than TTL | Normal render + "Last updated X ago" subtitle + refresh icon |
  | Offline | Network down | Gray banner: "You're offline" |

  ### Interactive States
  | State | Trigger | Visual Treatment |
  |-------|---------|-----------------|
  | Default | Rest | Normal styling |
  | Hover | Mouse enter | Background lighten/darken, cursor pointer |
  | Active/Pressed | Mouse down | Slight scale down (0.98) or darken |
  | Focused | Tab key | 2px ring in --color-ring, offset 2px |
  | Selected | Click | Background accent, checkmark, left border |
  | Disabled | Condition | 50% opacity, cursor not-allowed, no hover |
  | Dragging | Drag start | Elevated shadow, slight rotation, ghost placeholder |

  ### Form States
  | State | Trigger | Visual Treatment |
  |-------|---------|-----------------|
  | Pristine | Initial | Normal borders |
  | Touched | Blur after focus | No change (until validation) |
  | Valid | Passes validation | Green checkmark right of input (optional) |
  | Invalid | Fails validation | Red border, red error text below, field shakes (optional) |
  | Submitting | Form submit | Inputs disabled, button shows spinner |
  | Submit Success | API success | Toast success, form resets or navigates |
  | Submit Error | API failure | Toast error OR inline error banner |

  Required State Mockups

  The designer must provide visual examples of at minimum:
  - Loading skeleton for every page/panel type
  - Empty state for every list/table/grid
  - Error state for API-dependent views
  - Form validation error state
  - Toast notifications (all 4 types)
  - Confirmation dialog (destructive action)
  - Disabled/readonly form fields
  - Mobile versions of all modals → converted to bottom sheets

  8. ACCESSIBILITY CONTRACT

  8A. ARIA Requirements Per Component Type

  Buttons:        aria-label (if icon-only), aria-disabled, aria-pressed (toggles)
  Inputs:         aria-label or aria-labelledby, aria-describedby (errors/help), aria-invalid, aria-required
  Modals:         role="dialog", aria-modal="true", aria-labelledby (title)
  Tabs:           role="tablist" / role="tab" / role="tabpanel", aria-selected
  Alerts:         role="alert" (for errors), role="status" (for success)
  Live regions:   aria-live="polite" (data updates), aria-live="assertive" (errors)
  Navigation:     role="navigation", aria-current="page"
  Menus:          role="menu" / role="menuitem", aria-expanded
  Progress:       role="progressbar", aria-valuenow, aria-valuemin, aria-valuemax
  Tooltips:       role="tooltip", connected via aria-describedby

  8B. Focus Management Rules

  Tab order:        Follows visual order (left→right, top→bottom)
  Modal open:       Focus moves to first focusable element inside
  Modal close:      Focus returns to trigger element
  Sheet open:       Focus moves inside, trapped until close
  Dropdown open:    Focus on first item, arrow keys navigate
  Form submit:      If error, focus moves to first invalid field
  Page navigation:  Focus moves to page heading (h1)
  Toast appear:     Focus NOT stolen (aria-live announces instead)

  8C. Keyboard Shortcuts

  Document all keyboard shortcuts in the application:

  ⌘K / Ctrl+K:     Open command palette
  Escape:           Close modal/sheet/dropdown/command palette
  Enter:            Submit form / confirm dialog / activate button
  Tab / Shift+Tab:  Move focus forward/backward
  Arrow Up/Down:    Navigate menu items, table rows
  Arrow Left/Right: Navigate tabs
  Space:            Toggle checkbox/switch, activate button
  Delete/Backspace: Remove selected item (with confirmation)
  ⌘S / Ctrl+S:     Save current form (if applicable)

  8D. Color Contrast Requirements

  Normal text (< 18px):     4.5:1 minimum contrast ratio
  Large text (≥ 18px bold): 3:1 minimum contrast ratio
  UI components:            3:1 minimum contrast ratio
  Focus indicators:         3:1 against adjacent colors
  Status colors on white:   Must pass independently (don't rely only on color)

  10A. Visual Regression Regions

  10B. Interaction Test Scenarios

  For each major user workflow, provide a numbered sequence using test IDs. The developer translates these 1:1 into Playwright tests.

  Template:
  Scenario: [Name]
  Precondition: [Login state, data state]
  1. Click [data-testid="..."]
  2. Verify [element] is visible
  3. Type "..." into [data-testid="..."]
  4. Select "..." from [data-testid="..."]
  5. Click [data-testid="..."]
  6. Verify toast "..." appears
  7. Verify [data-testid="..."] shows "..."

  Provide at least one scenario per:
  - CRUD operation (create, read, update, delete)
  - Filter/search flow
  - Navigation flow
  - Error recovery flow
  - Role-restricted access flow

  10C. Accessibility Test Checklist Per Page

  ☐ All images have alt text (or aria-hidden if decorative)
  ☐ Page has exactly one h1
  ☐ Heading hierarchy is sequential (h1 → h2 → h3, no skips)
  ☐ All form inputs have visible labels
  ☐ Error messages are linked to inputs via aria-describedby
  ☐ Focus is visible on all interactive elements
  ☐ Tab order matches visual order
  ☐ Modals trap focus
  ☐ Color is not the only indicator (icons/text accompany color status)
  ☐ Text resizes without breaking layout (up to 200%)
  ☐ No auto-playing media
