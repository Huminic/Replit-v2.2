  This will give a very focused agent understanding and documentation of the Venn solutions interface.       The VIN Solutions integration is full of hard-won knowledge. Header casing (v3 not V3), href reference    
  formats for contacts/leadSources/leadTypes, the 2-step lead creation flow, which endpoints use
  application/json vs application/vnd.coxauto.v3+json, the items not results response key. All of that is   
  currently buried inside vinSolutionsService.ts in nexxus-v2. If you ever need VIN data from another app —
  or even from a Claude session doing research — you'd have to rediscover all of it.

  MCP tools are self-documenting. When a Claude session connects to the MCP server, it sees the tool        
  definitions — parameters, descriptions, what each endpoint does. That's living documentation that any
  agent can read and use correctly without needing to understand the nexxus codebase.                       
                                                                  
  It's also a safety boundary. One of the problems tonight was that VIN lead polling was wired directly into
   the trigger engine inside nexxus. Internal function calls are invisible — they just fire. An MCP tool is
  an explicit request with a clear interface. It's harder to accidentally wire an MCP tool into a background
   job that spams customers.                                      

  Practical considerations:

  The MCP server would need either access to the same database or its own token store
  - The existing VinOAuthService and VinSolutionsService are portable — they're already self-contained with 
  a Pool dependency                                                                                         
  - Your central-mcp is already running (PM2 id 14, online) so the infrastructure is there
