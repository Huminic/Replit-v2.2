  My Honest Advice

  Your instinct is right, but with one refinement:

  1. Keep the backend. It works. 237 endpoints, 40 services, 8 scheduled jobs, 7 integrations — all wired and tested. Rebuilding this would be months of rework for zero new capability.
  2. Replace the frontend against the new design. This is where the drift happened. A clean client rebuild against the designer's handoff, wired to the existing API, is the right move.
  3. The Reverse SRS + audit files are your bridge. They document exactly what the backend exposes, so the new frontend knows what to connect to. Include docs/REVERSE_SRS.md and docs/audit/server-audit.md in your
  handoff folder — they're the API contract.
  4. init-project could work, but verify what it actually sets up. If it creates a brand new project structure, you'd lose the backend. If it can be pointed at just the client/ directory with new governance, that's
  ideal.

  One Risk to Flag

  "Disregard the current UI completely" is emotionally satisfying but practically dangerous. Some things in the current frontend are load-bearing:

  - fetchApi() wrapper with JWT refresh logic
  - TanStack Query hooks (26 of them) that know the API contract
  - SSE streaming for DealerBrain
  - Organization context switching for Partner Admins
  - Webhook event handling

  These aren't "UI" — they're integration plumbing. A new frontend still needs all of this. The designer's screens won't include it.

  Recommendation: Frame it as "new UI shell and components, preserve integration plumbing" rather than "disregard everything."
